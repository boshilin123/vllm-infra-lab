# Phase 4 双副本确定性 8/8 分流对照

## 实验问题

普通 Kubernetes ClusterIP Service 双副本实验已经证明两张 A10 能提高吞吐，但单波次连接分配偏斜使部分请求进入 waiting，P95 TTFT/E2E 仍未满足 Short SLO。本对照保持计算资源、模型、负载和并发不变，只把入口改为两条并行的 Pod IP 直连 c8 流，验证瞬时分流是否是此前尾延迟的主要原因。

## 环境与控制变量

- Git commit：`9d0f499fa25d1226ed681e7fe2aff57ee940e830`
- 服务端：vLLM 0.9.1，两个 Qwen3-8B BF16/A10 副本，节点 `qhvgpu1`
- GPU：原副本使用物理 GPU 1，新副本使用物理 GPU 2；UUID 见 `metadata.yaml`
- 每副本：`max-num-seqs=8`、`max-model-len=4096`、`gpu-memory-utilization=0.85`
- 总负载：256 Prompt Token / 128 Output Token，总并发 16
- 确定性分流：两个子任务同步启动，各自直连一个 Pod，以 c8 处理每轮 50 个正式请求；两侧使用相同 seed
- 正式请求：每轮合计 100、共 3 轮；300/300 成功
- 持久性：benchmark 和 5 秒监控分别运行于宿主机 root tmux；benchmark 退出码为 0

结果目录使用 benchmark client 容器的本地时区 `-07:00` 生成 `023250` 时间戳；宿主机监控使用 Asia/Shanghai，窗口为 `17:32:37–17:40:32`。两者是同一实验窗口，不是系统时钟错误。

## 三轮合并结果

合并延迟由两侧共 100 个逐请求样本重新计算，不对两个 P95 做平均。吞吐分母取两个近同步子任务中较长的测量时长，因此不会把两侧串行相加，也不会因较快一侧提前结束而夸大结果。

| Repeat | 成功 | Output throughput (tok/s) | P95 TTFT (ms) | P95 TPOT (ms) | P95 E2E (ms) | 两侧时长差 (ms) |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 100/100 | 335.586 | 522.569 | 42.591 | 5533.922 | 99.251 |
| 2 | 100/100 | 334.824 | 524.631 | 42.721 | 5545.558 | 139.261 |
| 3 | 100/100 | 334.755 | 526.738 | 42.706 | 5543.586 | 108.016 |
| **中位数** | **300/300** | **334.824** | **524.631** | **42.706** | **5543.586** | **108.016** |

输出吞吐 CV 为 0.138%，P95 TTFT/TPOT/E2E 的 CV 分别为 0.397%/0.167%/0.112%，三轮重复性稳定。

## 与已有基线对照

| 配置 | Output throughput (tok/s) | P95 TTFT (ms) | P95 TPOT (ms) | P95 E2E (ms) |
| --- | ---: | ---: | ---: | ---: |
| 单副本 c8-mns8（历史） | 178.796 | 524.927 | 42.740 | 5554.010 |
| 单副本 c16-mns8 | 179.285 | 6015.515 | 42.703 | 11095.317 |
| 单副本 c16-mns16 | 305.434 | 976.838 | 46.768 | 6152.403 |
| 普通 Service 双副本 c16-mns8 | 332.912 | 5469.014 | 42.484 | 10741.813 |
| **确定性 8/8 双副本 c16-mns8** | **334.824** | **524.631** | **42.706** | **5543.586** |

- 相对单副本 c16-mns8，输出吞吐提高 **86.75%**，P95 TTFT 降低 **91.28%**，P95 E2E 降低 **50.04%**。
- 相对普通 Service 双副本，输出吞吐仅提高 **0.57%**，但 P95 TTFT 降低 **90.41%**、P95 E2E 降低 **48.39%**。这说明两种入口拥有近似的总计算容量，但普通 Service 的瞬时偏斜把少数请求推入了完整波次排队。
- 相对单副本 c8，P95 TTFT/TPOT/E2E 分别只变化 `-0.06%/-0.08%/-0.19%`，而输出吞吐达到其 1.873 倍；相对两倍历史 c8 的线性扩展效率为 **93.63%**。
- 相对单副本 c16-mns16，输出吞吐仍高 **9.62%**，且三个 P95 延迟均更低。

## 每副本运行时证据

`live-monitor.log`覆盖探测、预热、三轮正式负载和收尾。counter 增量包含每侧 150 个正式请求、24 个预热请求及 6 个 benchmark 初始探测，因此每侧均为 180，而正式结果本身由 target JSON 直接确认各为 150/150。

| Pod / GPU | 全流程完成增量 | Prompt / Generation Token 增量 | Peak running | Peak waiting | Peak KV Cache | Peak GPU-Util |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 原副本 / GPU 1 | 180 | 46043 / 23040 | 8 | 0 | 13.525% | 100% |
| 新副本 / GPU 2 | 180 | 46043 / 23040 | 8 | 0 | 13.525% | 100% |

两侧请求和 Token counter 增量完全相同，负载主体都达到 `running=8`，而整个采样窗口 `waiting=0`。这比“整场累计约 50/50”更强：它直接排除了普通 Service 实验中一侧排队、另一侧有空槽的单波次偏斜。GPU 0 显存始终约 5901 MiB、利用率 0%，GPU 3 始终约 1 MiB；两个 vLLM Pod 均 0 restart、abort 增量为 0。

## 预注册验收

| 条件 | 结果 | 判定 |
| --- | --- | --- |
| 成功率 ≥99% | 300/300，100% | PASS |
| 输出吞吐 ≥300 tok/s | 334.824 tok/s | PASS |
| P95 TTFT ≤600 ms | 524.631 ms | PASS |
| P95 TPOT ≤50 ms | 42.706 ms | PASS |
| P95 E2E ≤6000 ms | 5543.586 ms | PASS |
| 每副本主体 `running≈8、waiting=0` | Peak running 8/8，Peak waiting 0/0 | PASS |
| 公司服务与两卡安全边界 | 公司 GPU 0未变化；已恢复单副本并释放 GPU 2 | PASS |

**总判定：预注册条件全部通过。** 静态扩容已经证明两张卡的容量有效；本轮进一步证明，在相同双副本容量下，确定性均衡分流能把 P95 TTFT/E2E 恢复到单副本 c8 水平。普通 ClusterIP Service 的连接级、非队列感知单波次分配，是此前尾延迟失败的主要原因。

这是因果对照，不是生产路由器实现。直连 Pod IP 缺少服务发现、故障转移和动态负载感知，因此不能声称已经完成队列感知路由或 HPA/KEDA。生产方向应让请求级路由与副本扩缩容分工：前者选择当前更空闲的副本，后者改变可用容量。

## 安全回退

实验后重新应用 base `deploy/kubernetes`，删除临时 benchmark client，并等待 rollout 完成。最终 Deployment 为 `desired/ready/current/available=1/1/1/1`，只保留原 Pod、restart 0；GPU 2由约 20 GiB 回落到 1 MiB，GPU 0保持约 5901 MiB且利用率 0%。
