# Decode 对照：256/256 c8-mns8

## 实验问题

相对同卡 Short 校准，只把输出从 128 增加到 256 tokens，Prompt 仍为 256，验证输出长度翻倍是否改变逐 Token 节奏，以及额外 Decode Token 如何累积到 E2E。

事前假设是 TPOT 不会随输出长度翻倍，E2E 增量约为新增 `128 × 40 ms ≈ 5.1 s`。

## 实验配置

- 模型：Qwen3-8B BF16，vLLM 0.9.1
- 输入/输出长度：256/256 tokens
- 客户端并发 / 服务端 `max-num-seqs`：8/8
- 每轮预热/正式请求：10/60，正式重复 3 次
- 节点、GPU UUID：qhvgpu1，`GPU-5e5590e5-51de-1c1c-6c72-4cbe1477e116`
- Git commit：`da604fe15147b72a7341b7370eef168eef1d8c05`
- 正式随机种子：`207042/207043/207044`

实测 P95 E2E 增量为：

```text
10593.705 - 5496.814 = 5096.890 ms
```

与事前粗估的 5.1 秒几乎一致。输出长度翻倍后，请求完成率约减半，但输出 Token 吞吐基本持平；P95 TPOT 反而小幅下降 2.16%，属于“逐 Token 节奏没有明显恶化”，而不是生成速度翻倍。

## KV Cache 与 SLO

正式阶段主要观察到 `running=8、waiting=0`。KV Cache 峰值约 18.01%，与满长度上界 `8 × (256+256) / 22832 ≈ 17.94%` 接近，微小差异可由 block 对齐、缓存残留和采样时刻解释。

| 指标 | Long SLO | 实测 | 判断 |
| --- | ---: | ---: | --- |
| 请求成功率 | ≥99% | 100% | PASS |
| P95 TTFT | ≤1500 ms | 525.221 ms | PASS |
| P95 TPOT | ≤55 ms | 41.041 ms | PASS |
| P95 E2E | ≤13 s | 10.594 s | PASS |

结论是：在这一固定并发下，输出变长主要通过更多 Decode 步数线性累积 E2E，并未明显改变每一步的 TPOT。该结论只适用于 256-token 输出范围，不能外推到接近 `max-model-len` 或 KV Cache 压力更高的场景。
