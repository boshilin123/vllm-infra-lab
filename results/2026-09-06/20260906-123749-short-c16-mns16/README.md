# Short 参数实验：c16-mns16

## 实验目的

保持客户端并发 16、Qwen3-8B BF16、256/128 Token、单张 A10、`max-model-len=4096` 和 `gpu-memory-utilization=0.85` 不变，只把服务端 `max-num-seqs` 从 8 提高到 16，验证更宽运行批次能否消除 waiting、提升吞吐并改善 c16 的 TTFT/E2E。

`c16-mns8` 表示客户端并发 16、服务端最多运行 8 条序列；`c16-mns16` 表示客户端并发和服务端上限均为 16。

## 事前假设

实验执行者最初预计 `running=0、waiting=0`、输出吞吐提高 80%–90%、TTFT 和 E2E 改善并满足 SLO、KV Cache 约 27%；如果延迟仍不满足 SLO则选择 mns8。

校正后的假设是：稳定阶段 `running≈16、waiting≈0`；吞吐暂以提高 20%–60%为宽范围；TTFT 会显著改善但不预设通过 600 ms，TPOT 可能因批次变宽而恶化，E2E 也不预设通过 6 s；KV Cache 预计约 25%–30%。若单副本 c16 仍违反 SLO，应限制入口并发或通过多副本扩容，而不是让 mns8 在服务端继续排队。

## 实验配置

- 输入/输出长度：256/128 tokens
- 客户端最大并发：16
- 服务端 `max-num-seqs`：16
- 服务端 `max-model-len`：4096
- 服务端 `gpu-memory-utilization`：0.85
- 每轮预热/正式请求：10/100
- 正式重复：3 次
- 客户端与服务端 vLLM：0.9.1
- 服务节点：qhvgpu1
- 宿主机物理 GPU：3
- GPU UUID：`GPU-c9ee2ea8-993d-e7e2-7e3f-7a183b63d573`
- Git commit：`ca85714ea9957b12cdec28cd39be405c9f81e42a`
- 正式随机种子：`15042/15043/15044`

新 Pod 启动日志直接报告 KV Cache 总容量为 3.14 GiB、22,832 tokens、1,427 blocks，且启动参数确认 `max_num_seqs=16`。

## 与 c16-mns8 对比

| 指标 | c16-mns8 | c16-mns16 | 相对变化 |
| --- | ---: | ---: | ---: |
| 请求吞吐 | 1.400668 req/s | 2.386205 req/s | +70.36% |
| 输出吞吐 | 179.285466 tok/s | 305.434290 tok/s | +70.36% |
| Mean TTFT | 5471.729266 ms | 673.062321 ms | -87.70% |
| P95 TTFT | 6015.514603 ms | 976.837920 ms | -83.76% |
| Mean TPOT | 40.260742 ms | 42.619063 ms | +5.86% |
| P95 TPOT | 42.703375 ms | 46.768354 ms | +9.52% |
| Mean E2E | 10583.944401 ms | 6085.688662 ms | -42.50% |
| P95 E2E | 11095.316810 ms | 6152.403065 ms | -44.55% |

mns16 消除了服务端 waiting，并将输出吞吐提高约 126.15 tok/s，但没有随运行序列数翻倍而使吞吐翻倍。更宽批次提高了单次调度推进的序列数，同时也让各序列共享同一张 GPU 的计算和内存带宽，P95 TPOT 上升约 9.52%，所以扩展不是线性的。

## TTFT、TPOT 与 Chunked Prefill

正式阶段稳定观察到 `running=16、waiting=0`。waiting 为 0 只表示请求已被调度，不表示它们能够立即完成 Prefill。

启动日志显示 `max_num_batched_tokens=2048` 且 Chunked Prefill 已启用。首波 16 个请求共有：

```text
16 × 256 = 4096 prompt tokens
```

4096 大于每次调度可处理的 2048 tokens，因此首波 Prompt 至少需要分块推进；再叠加 16 条序列竞争 GPU，P95 TTFT 虽从 6.02 秒降到 0.98 秒，仍没有达到 600 ms。

TPOT 不包含完整的调度前 waiting，但会反映 Decode 阶段更宽批次的资源竞争，所以 P95 TPOT 从 42.70 ms 上升到 46.77 ms。TTFT 的大幅改善抵消了大部分 Decode 变慢，P95 E2E 从 11.10 秒降到 6.15 秒，但仍比 6 秒 SLO 高约 152 ms。

## KV Cache 与 GPU 观测

采样观察到：

- `running=16、waiting=0`
- KV Cache 采样峰值约 24.18%，常见高位约 22.49%
- GPU-Util 约 96%–100%
- 功耗约 148–151 W
- 温度最高约 71°C
- 无 OOM、CUDA error 或 preemption 日志

16 条 384-token 序列全部同时达到最大长度时，简单上界约为：

```text
16 × 384 ÷ 22832 ≈ 26.91%
```

实测采样峰值 24.18%略低，最直接的解释是序列进度和完成时刻不完全同步，加上 3 秒采样未必捕获理论瞬时峰值。PagedAttention 的 block 动态分配减少了连续显存和碎片压力，但不能仅凭低于 27%就证明批处理效率更高。

## 算术一致性

```text
2.386205393 requests/s × 128 tokens/request
= 305.434290 tok/s

673.062321 + 127 × 42.619063
≈ 6085.683 ms
```

后一结果与实测 Mean E2E `6085.689 ms` 只相差约 0.005 ms，数据自洽。

## Short SLO v1

| 指标 | SLO | c16-mns16 | 判断 |
| --- | ---: | ---: | --- |
| 请求成功率 | ≥99% | 100% | PASS |
| P95 TTFT | ≤600 ms | 976.838 ms | **FAIL** |
| P95 TPOT | ≤50 ms | 46.768 ms | PASS |
| P95 E2E | ≤6 s | 6.152 s | **FAIL** |
| 请求吞吐 CV | ≤3% | 0.308% | PASS |

mns16 比 mns8 更适合承接单副本突发吞吐，但在客户端并发 16 下仍不满足既定 TTFT/E2E SLO，因此不能把“吞吐提高”直接写成“配置优化完成”。

## 实验执行者复盘与校正

实验执行者认为：吞吐没有翻倍可能因为批处理效率不能完全跑满；TTFT 从 6 秒以上降到约 1 秒已经非常可观；TPOT 上升是因为并发从 8 到 16 后处理内容更多；KV 低于 27%得益于 PagedAttention；最终选择单副本限制到并发 8、用两个副本承接总并发 16，因为 mns8 单副本无法满足高并发，而 mns16 仍有指标超过 SLO。

其中容量扩展选择正确。需要补充的是：吞吐未线性翻倍可由 TPOT 上升直接量化，说明更宽批次增加资源竞争；TTFT 的下降值得肯定，但 SLO 判断仍以绝对阈值为准；PagedAttention 是低碎片动态管理 KV 的基础机制，24.18%低于理论上界的主要测量解释仍是序列不同步与采样间隔。

## 结论与下一步

- mns8→mns16 将单卡 c16 输出吞吐提高 70.36%，证明此前 179 tok/s 的平台主要由 `max-num-seqs=8` 配置上限造成，而不是 KV Cache 容量上限。
- mns16 在 c16 下仍违反 P95 TTFT 和 P95 E2E SLO，单卡不能同时满足当前 16 并发目标和全部体验阈值。
- 下一步架构方向是每副本限制约 8 并发，以两个 GPU 副本分担总并发 16；正式实施前还需确认第二张 GPU、模型存储、路由均衡和监控标签，不能把计划写成已完成。
- 在多副本实验前，应恢复或单独固化每副本 `max-num-seqs=8`，并预注册“两个副本是否各承接约 8 请求、总吞吐是否接近单副本 c8 的两倍、P95 是否继续满足 SLO”的假设。
