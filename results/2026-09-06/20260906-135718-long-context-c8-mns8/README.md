# 组合长上下文：1024/256 c8-mns8

## 实验问题

在相同 Pod、GPU、并发和服务端参数下，同时把 Prompt 从 256 增至 1024、输出从 128 增至 256，观察 Prefill 与 Decode 压力叠加后的吞吐、尾延迟、KV Cache 和 Long SLO 结果。

## 实验配置

- 模型：Qwen3-8B BF16，vLLM 0.9.1
- 输入/输出长度：1024/256 tokens
- 客户端并发 / 服务端 `max-num-seqs`：8/8
- `max-model-len` / `gpu-memory-utilization`：4096/0.85
- 每轮预热/正式请求：10/60，正式重复 3 次
- 节点、GPU UUID：qhvgpu1，`GPU-5e5590e5-51de-1c1c-6c72-4cbe1477e116`
- Git commit：`da604fe15147b72a7341b7370eef168eef1d8c05`
- 正式随机种子：`307042/307043/307044`

三轮均为 60/60 请求成功，失败数为 0；时长分别为 97.30、97.16、97.18 秒。吞吐与 E2E 很稳定，P95 TTFT 的跨轮 CV 为 8.55%，再次显示 Prefill 尾延迟比稳态 Decode 更敏感。

## 四场景总览

| 场景 | 输入/输出 | 输出吞吐 tok/s | P95 TTFT ms | P95 TPOT ms | P95 E2E ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| Short 校准 | 256/128 | 180.649 | 486.415 | 41.948 | 5496.814 |
| Prefill 对照 | 1024/128 | 139.004 | 1464.014 | 53.147 | 7354.942 |
| Decode 对照 | 256/256 | 182.642 | 525.221 | 41.041 | 10593.705 |
| 组合长上下文 | 1024/256 | 158.052 | 1426.444 | 47.145 | 12788.777 |

相对 Short，组合场景的输出吞吐下降 12.51%，P95 TTFT 上升 193.26%，P95 TPOT 上升 12.39%，P95 E2E 上升 132.66%。相对 Decode 对照只增加 Prompt 后，输出吞吐下降 13.46%、P95 TTFT 上升 171.59%、P95 E2E 上升 20.72%，直接体现更长 Prefill 的代价。

不能用 Prefill 对照到组合场景的输出吞吐 `+13.70%`证明引擎更快：输出 Token 变多后，固定 Prefill 成本被更多生成 Token 摊薄，而请求吞吐实际下降 43.15%。

## KV Cache、调度和 GPU

KV Cache 采样峰值为 44.36%，接近满长度简单上界：

```text
8 × (1024 + 256) / 22832 ≈ 44.85%
```

正式阶段主要为 `running=8、waiting=0`，曾短暂观察到 waiting 后重新填满批次；这与 Chunked Prefill 的 token budget 和序列补入过程一致，不代表超过 `max-num-seqs=8`。后半程可复核监控峰值为 GPU-Util 100%、功耗 155.35 W、温度 72°C；监控滚动缓冲未覆盖四组实验全程，因此这些值只作为本轮后半程采样证据。

实验结束后的严格审计确认 Pod `Ready=true`、Running、0 次重启，近两小时系统故障级日志、HTTP 4xx/5xx 和 namespace Warning Event 均为 0。最初用宽泛关键词搜索得到的数百条命中来自 INFO 日志记录的随机 Prompt，其中自然包含 Error、Traceback 等单词，不能当作服务异常。

## Long SLO v1

| 指标 | SLO | 实测 | 判断 |
| --- | ---: | ---: | --- |
| 请求成功率 | ≥99% | 100% | PASS |
| P95 TTFT | ≤1500 ms | 1426.444 ms | PASS |
| P95 TPOT | ≤55 ms | 47.145 ms | PASS |
| P95 E2E | ≤13 s | 12.789 s | PASS |

P95 TTFT 余量约 74 ms，P95 E2E 余量约 211 ms；P99 TTFT 为 1680.417 ms，P99 E2E 为 13033.939 ms。Long SLO 预先定义的是 P95，所以本次判定仍为通过，但 P99 已揭示更严格尾部目标的风险，不能事后更换统计口径，也不能描述为容量充裕。

## 结论与边界

- 四种负载均无请求失败；组合长上下文通过预注册的全部 P95 Long SLO。
- Prompt 增长主要推高 TTFT 并占用 Prefill 算力，输出增长主要按 Decode 步数累积 E2E；两者叠加后 P95 E2E 已接近 13 秒边界。
- KV Cache 使用率低于 50%，说明本场景没有触及 KV 容量上限；它不证明计算、调度或 SLO 仍有同等比例余量。
- 下一步应从原始结果生成跨并发与四场景性能图，再进入 Phase 3 Dashboard/统一时间线，而不是立即占用第二张 GPU。
