# Short 场景：并发 2

## 实验目的

在模型、Pod、GPU、输入/输出长度和请求数量不变的条件下，将客户端最大并发从 1 提高到 2，验证 Continuous Batching 带来的吞吐收益和单请求延迟代价。

## 事前假设

该假设在查看并发 2 数据前已记录于并发 1 报告：

- 请求吞吐和输出 Token 吞吐上升，但不严格翻倍。
- TTFT、TPOT 和 E2E 上升。
- TTFT 也存在基本不变的可能，需要由实验判断。

## 实验配置

- 输入长度：256 tokens
- 输出长度：128 tokens
- 并发：2
- 每轮预热请求：10
- 每轮正式请求：100
- 正式实验重复：3 次
- vLLM：0.9.1
- 服务节点：qhvgpu1
- 宿主机物理 GPU：3
- GPU UUID：`GPU-c9ee2ea8-993d-e7e2-7e3f-7a183b63d573`
- Git commit：`4f443cd4d6876d6056b864f4fea9a8542192e54f`

本档位使用独立种子 `1042/1043/1044`，避免命中并发 1 遗留的 Prefix Cache。

## 三轮中位结果

| 指标 | 中位数 | CV |
| --- | ---: | ---: |
| 请求吞吐 | 0.398863 req/s | 0.0627% |
| 输出 Token 吞吐 | 51.054496 tok/s | 0.0627% |
| 总 Token 吞吐 | 153.163487 tok/s | 0.0627% |
| Mean TTFT | 134.906244 ms | 0.1061% |
| Mean TPOT | 38.413134 ms | 0.0629% |
| Mean E2E | 5013.367304 ms | 0.0637% |
| P95 E2E | 5025.727483 ms | 0.0228% |

三轮正式实验均为 100/100 请求成功，非空错误数为 0。

## 与并发 1 对比

| 指标 | 并发 1 | 并发 2 | 相对变化 |
| --- | ---: | ---: | ---: |
| 请求吞吐 | 0.221521 req/s | 0.398863 req/s | +80.1% |
| 输出 Token 吞吐 | 28.354627 tok/s | 51.054496 tok/s | +80.1% |
| Mean TTFT | 73.899712 ms | 134.906244 ms | +82.6% |
| Mean TPOT | 34.963472 ms | 38.413134 ms | +9.9% |
| Mean E2E | 4513.756706 ms | 5013.367304 ms | +11.1% |

吞吐提升到并发 1 的约 1.80 倍，而不是严格 2 倍，说明批处理提高了 GPU 总体效率，但两个序列仍需共享同一张 GPU 的计算和内存带宽。

## E2E 增量解释

并发 1 到并发 2：

```text
TTFT 增量 ≈ 134.91 - 73.90 ≈ 61 ms
TPOT 增量 ≈ 38.41 - 34.96 ≈ 3.45 ms/token
Decode 累积增量 ≈ 127 × 3.45 ≈ 438 ms
E2E 预计增量 ≈ 61 + 438 ≈ 499 ms
```

实际 Mean E2E 增加约 500 ms，与该拆解一致。虽然 TTFT 的相对增幅约为 83%，但它在单次请求中只出现一次；TPOT 的约 10% 增幅会在后续 127 个输出 Token 上累积，因此 E2E 主要受 Decode 阶段影响。

## 假设验证与边界

事前假设的五个方向均与结果一致。若业务更看重单请求延迟，并发 1 的当前结果更优；若更看重单位时间内的总体处理能力，并发 2 提供了明显收益。

这里的“并发 1 或 2”是压测客户端施加的负载条件，不是简单的服务端模式开关。生产系统通常通过限流、排队、请求批处理和副本数量，在吞吐目标与延迟 SLO 之间取舍，而不是永久把所有流量限制成固定并发。

当前结论仅适用于本次单节点、单 GPU、固定 256/128 Token、同节点端口转发的实验条件，尚不能说明更高并发下收益是否继续增长，也不能确定系统饱和点。

## 并发 4 的事前假设

实验执行者最初预测：并发 2 提高到 4 后，吞吐再提高约 80%，TTFT 再提高约 80%，TPOT 和 E2E 再提高约 10%；系统饱和时首先关注 `vllm:num_requests_waiting`。

在执行前将其修正为以下可检验假设：

- 请求吞吐和输出 Token 吞吐继续上升，但增幅未知，且预计不会严格翻倍。
- 随着单张 GPU 同时处理更多序列，TTFT、TPOT 和 E2E 预计上升，但不能根据一个并发区间直接假定相同百分比。
- 吞吐的边际增益下降，同时 TPOT 或 P95 E2E 持续上升，是接近计算饱和的早期信号。
- 并发 4 仍低于服务端 `max-num-seqs=8`，因此 `vllm:num_requests_waiting` 可能保持为 0；若它持续大于 0，则说明还受到 Token Budget、KV Cache 或调度容量限制。
- `max-concurrency=4` 只允许四个请求进入客户端发送阶段，其余请求在客户端等待，不会被服务端的 `vllm:num_requests_waiting` 统计。

以上内容在查看并发 4 数据前记录。实验完成后同时验证吞吐—延迟趋势和 Prometheus 中的 running/waiting requests，避免只用单个指标定义“饱和”。
