# Short 场景：并发 4

## 实验目的

在其他条件不变时，将客户端最大并发从 2 提高到 4，验证批处理吞吐的边际收益，并观察服务端是否开始排队。

## 事前假设

实验执行者最初预测吞吐继续提高约 80%，TTFT 提高约 80%，TPOT 和 E2E 提高约 10%，并将 `vllm:num_requests_waiting` 作为饱和信号。执行前保留方向判断，但不再把并发 1→2 的百分比线性外推到并发 2→4。

## 实验配置

- 输入长度：256 tokens
- 输出长度：128 tokens
- 并发：4
- 每轮预热请求：10
- 每轮正式请求：100
- 正式实验重复：3 次
- vLLM：0.9.1
- 服务节点：qhvgpu1
- 宿主机物理 GPU：3
- GPU UUID：`GPU-c9ee2ea8-993d-e7e2-7e3f-7a183b63d573`
- Git commit：`6c5cf89f05fc3f4f4f2d8caa40ba089e081cba88`
- 正式随机种子：`3042/3043/3044`

## 与并发 2 对比

| 指标 | 并发 2 | 并发 4 | 相对变化 |
| --- | ---: | ---: | ---: |
| 请求吞吐 | 0.398863 req/s | 0.769253 req/s | +92.9% |
| 输出 Token 吞吐 | 51.054496 tok/s | 98.464412 tok/s | +92.9% |
| Mean TTFT | 134.906244 ms | 238.705613 ms | +76.9% |
| Mean TPOT | 38.413134 ms | 39.078182 ms | +1.7% |
| Mean E2E | 5013.367304 ms | 5198.595218 ms | +3.7% |

吞吐提升比事前猜测的 80%更接近翻倍；TTFT 增幅接近预测；TPOT 和 E2E 的增幅则明显低于预测。

## 为什么 GPU-Util 约 97% 时吞吐仍能提高

`nvidia-smi` 的 GPU-Util 主要表示采样窗口内 GPU 有多少时间在执行计算，不等价于已经达到最大有效 FLOPS、SM Occupancy、Tensor Core利用率或显存带宽。并发 2 和并发 4 都可以让 GPU 长时间保持忙碌，但批宽为 4 时，同一轮模型权重读取和内核执行可以推进更多序列，因此单位时间完成的 Token 更多。

本实验同节点通信、网络数据量较小，且三轮吞吐 CV 约为 0.12%；这些证据不支持将吞吐提升解释为网络波动。

## 为什么 TPOT 基本不变但总体吞吐接近翻倍

TPOT 是单个请求相邻输出 Token 的平均间隔。并发 4 时，每个请求的 TPOT 只比并发 2 增加约 1.7%，但一次 Decode 调度能同时推进约 4 个活跃序列。因此单请求 Token 节奏变化很小，总体输出 Token 数却接近按并发数增长。

输出吞吐也可由固定输出长度复算：

```text
0.769253 requests/s × 128 tokens/request ≈ 98.46 tokens/s
```

## E2E 增量解释

```text
TTFT 增量 ≈ 238.71 - 134.91 ≈ 104 ms
TPOT 增量 ≈ 39.08 - 38.41 ≈ 0.67 ms/token
Decode 累积增量 ≈ 127 × 0.67 ≈ 85 ms
预计 E2E 增量 ≈ 104 + 85 ≈ 189 ms
```

实际 Mean E2E 增加约 185 ms，与该拆解接近。

## 服务端指标与饱和判断

正式阶段的实时采样主要观察到：

- `vllm:num_requests_running=4`
- `vllm:num_requests_waiting=0`
- KV Cache 使用率约 5%–7%
- GPU-Util 约 96%–97%
- 温度约 67–70°C

并发 4 尚不能视为当前场景的吞吐饱和点：吞吐相对并发 2 仍提升约 93%，服务端没有等待请求，KV Cache 余量也很大。不过，如果业务的 TTFT SLO 低于约 239 ms，那么它可能已经触及服务质量边界；容量饱和与延迟 SLO 饱和不是同一个概念。

以上结论仅适用于单 GPU、固定 256/128 Token 和当前共享环境。下一步需要测试并发 8，判断达到 `max-num-seqs=8` 时吞吐边际收益和延迟是否发生明显变化。

## 并发 8 事前假设

实验执行者最初预计 c4→c8 的吞吐提高约 80%–90%，并认为结果会受到算力和显存容量影响。校正后不预设固定百分比：吞吐预计继续提高，但随着计算、显存带宽和调度瓶颈逐渐显现，边际增益可能低于 c2→c4 的 92.9%。当前短请求的 KV Cache 使用率仅约 5%–7%，因此显存容量暂不作为主要瓶颈假设。

在当前请求基本对应单条序列的场景下，客户端并发 8 等于服务端 `max-num-seqs=8`。稳定阶段预计 `running` 接近 8、`waiting` 接近 0；轮次切换或最后一批请求不足 8 个时，`running` 可以短暂下降。并发超过 8 后，额外请求才更可能进入服务端等待队列。

即使 GPU-Util 仍接近 97%，也要用输出 Token 吞吐、请求吞吐、TPOT、TTFT、P95 E2E、running/waiting 和错误共同判断批处理是否继续带来有效收益。若 GPU 忙碌比例近似不变而单位时间输出 Token 数继续明显增加，说明批处理效率仍在提高。

SLO 是服务等级目标，例如 P95 TTFT、P95 E2E 或成功率的目标阈值。当前项目尚未设定正式业务 SLO；依据 c1→c4 中 TTFT 比 TPOT 和 E2E 增长更快的趋势，事前预计交互式业务的 TTFT 最可能先触及延迟边界，但最终判断必须结合明确阈值和 c8 实测。
