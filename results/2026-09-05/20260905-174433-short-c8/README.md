# Short 场景：并发 8

## 实验目的

在模型、GPU、Token 长度和请求数不变时，将客户端最大并发从 4 提高到 8，验证达到服务端 `max-num-seqs=8` 时的吞吐收益、延迟代价与服务端排队情况。

## 事前假设

实验执行者最初预计 c4→c8 的吞吐提高约 80%–90%，并认为算力和显存容量会共同影响结果。校正后的可检验假设是不预设固定百分比：吞吐继续提高，但边际增益可能低于 c2→c4 的 92.9%；稳定阶段 `running` 接近 8、`waiting` 接近 0；当前短请求的 KV Cache 使用率较低，显存容量暂不作为主要瓶颈。

## 实验配置

- 输入长度：256 tokens
- 输出长度：128 tokens
- 并发：8
- 每轮预热请求：10
- 每轮正式请求：100
- 正式实验重复：3 次
- vLLM 客户端与服务端：0.9.1
- 服务节点：qhvgpu1
- 宿主机物理 GPU：3
- GPU UUID：`GPU-c9ee2ea8-993d-e7e2-7e3f-7a183b63d573`
- Git commit：`13b034344f87b983a174004c1d0dba6486a006fc`
- 正式随机种子：`7042/7043/7044`

## 算术一致性

固定每请求输出 128 tokens：

```text
1.396846 requests/s × 128 tokens/request
≈ 178.796288 tokens/s
```

与汇总值 `178.796299 tok/s` 的差异仅来自输入数字截断。

E2E 近似复算：

```text
452.407425 + 127 × 39.898263
≈ 5519.487 ms
```

与实测 Mean E2E `5516.847 ms` 相差约 2.64 ms（约 0.048%），数据在聚合精度范围内自洽。

## 服务端与 GPU 观测

正式阶段的实时采样主要观察到：

- `vllm:num_requests_running=8`
- `vllm:num_requests_waiting=0`
- GPU KV Cache 峰值约 13.52%
- GPU-Util 约 97%
- 功耗约 149–150 W
- 温度最高约 71°C

轮次尾部曾观察到 running 从 8 降到 4、1，这是最后一批请求逐步完成，不是并发失效。客户端并发与 `max-num-seqs` 都是 8，没有额外活跃请求进入服务端等待队列。

## KV Cache 容量估算

Qwen3-8B BF16 配置为 36 层、8 个 KV heads、head dimension 128。每个 Token 的 KV Cache 理论大小约为：

```text
2（K/V）× 36 × 8 × 128 × 2 bytes
= 147456 bytes
= 144 KiB/token
```

从指标最小步长约 `1/1427`、CUDA 默认 16 tokens/block 推算，本实例约有 1427 个 GPU KV blocks，即约 22832 个 Token slot、约 3.14 GiB KV Cache。这是基于配置与运行指标的估算，不替代启动日志中的直接容量数据。

c8 捕获到的 13.52%约对应 193 blocks、3088 Token slot、0.424 GiB，与 `8 × (256+128)=3072` 个活跃 Token 加 block 对齐/少量缓存残留相符。当前短请求距离 KV Cache 容量边界很远；在 `max-num-seqs=8` 不变时，c16 的额外请求预计主要等待，KV Cache 峰值未必显著高于 c8。

## 实验 SLO v1

为了在 c16 前建立前瞻性判断标准，从下一档实验起使用以下 Short 场景 SLO：

| 指标 | 目标 |
| --- | ---: |
| 请求成功率 | ≥99% |
| P95 TTFT | ≤600 ms |
| P95 TPOT | ≤50 ms |
| P95 E2E | ≤6 s |

请求吞吐 CV ≤3%作为实验重复性门槛，不属于服务体验 SLO。c8 按该标准回看全部通过，但这套阈值是在观察 c8 后定义的，不能把 c8 包装成预注册 SLO 验证；它从 c16 开始正式生效。

## 执行故障记录

首次由 Agent 启动时只直接调用了虚拟环境 Python，没有激活虚拟环境的 `PATH`，导致 runner 找到系统 `/usr/local/bin/vllm`。系统版本不接受客户端 0.9.1 使用的 `--endpoint-type openai`，预热在发出请求前失败。确认没有请求和正式结果后，删除了仅含 metadata 的无效目录；随后显式激活 `vllm-qwen3` 环境并重新运行，三轮正式结果均来自正确的 vLLM 0.9.1 客户端。

预防方式：运行 benchmark 前不仅要核对 Python 路径，还要确认 runner 输出的 vLLM 可执行文件位于 `/home/qhadmin/boshi/vllm/envs/vllm-qwen3/bin/vllm`。

## 当前结论与边界

- 容量饱和：c8 吞吐仍提高 81.58%，尚无吞吐平台或服务端 waiting，不能判定已经饱和。
- SLO 饱和：当前无法用事后定义的 SLO 对 c8 做预注册判断；按新阈值回看，c8 全部通过，其中 P95 TTFT 距边界最近。
- 稳定性：主要指标 CV 很低，只能说明本时段、本配置的三轮重复性好，不能单独证明网络无波动、测量无偏差或达到峰值。
- 适用范围：结论仅适用于单张 A10、Qwen3-8B BF16、256/128 Token、`max-num-seqs=8` 和当前共享环境。

## 并发 16 事前假设

实验执行者预计稳定阶段 `running=8、waiting=8`，并提出额外请求是否在 Prefill 的 block 上等待。更准确地说，额外请求预计位于 vLLM 调度器的 waiting 队列，尚未进入 RUNNING/PREFILL 阶段，也通常尚未占用完整的 GPU KV Cache block；它们被调度后才进行 Prefill 和 Decode。

实验执行者最初预计 c8→c16 吞吐提高 20%–40%，理由是 `max-num-seqs=8` 限制了同时执行序列数。校正后的假设是吞吐大致持平或只小幅提高，暂以 0%–10%作为待验证范围：c8 已能持续保持约 8 条序列运行，c16 主要把原本位于客户端的排队转移到服务端，未增加实际批宽；只有减少请求补入间隙等因素可能带来小幅收益。

实验执行者最初预计 TTFT、TPOT 和 P95 E2E 都突破 SLO。校正后预计 P95 TTFT 和 P95 E2E 最可能因服务端排队突破 600 ms 和 6 s；P95 TPOT 衡量请求进入执行后的逐 Token 间隔，预计仍接近 c8 的 42.74 ms，可能继续满足 50 ms 目标。成功率预计仍满足 ≥99%，但以实测为准。

KV Cache 峰值预计仍接近 c8 的约 13%–15%，而不是随客户端并发翻倍到约 27%。原因是 `max-num-seqs=8` 仍只允许约 8 条序列同时运行；waiting 请求主要占用队列和输入元数据，不会像运行中序列一样完整占用 GPU KV Cache。
