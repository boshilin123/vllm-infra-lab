# Short 场景：并发 16

## 实验目的

在模型、GPU、Token 长度和服务端 `max-num-seqs=8` 不变时，将客户端最大并发从 8 提高到 16，验证额外请求进入服务端 waiting 队列后，吞吐、排队延迟、KV Cache 和 Short SLO v1 如何变化。

## 事前假设

实验执行者最初预计稳定阶段 `running=8、waiting=8`，c8→c16 吞吐提高 20%–40%，TTFT、TPOT 和 P95 E2E 均突破 SLO，KV Cache 因 waiting 存在而仍接近 c8。

实验前校正并冻结的假设是：额外请求在 vLLM 调度器 waiting 队列等待，尚未进入 Prefill；c8 已能持续保持约 8 条序列运行，因此 c16 吞吐预计持平或只提高 0%–10%；P95 TTFT 和 P95 E2E 最可能因排队突破 SLO，P95 TPOT 仍接近 c8；只有运行中的约 8 条序列使用 GPU KV Cache，峰值预计仍约 13%–15%。

## 实验配置

- 输入长度：256 tokens
- 输出长度：128 tokens
- 客户端最大并发：16
- 服务端 `max-num-seqs`：8
- 每轮预热请求：10
- 每轮正式请求：100
- 正式实验重复：3 次
- vLLM 客户端与服务端：0.9.1
- 服务节点：qhvgpu1
- 宿主机物理 GPU：3
- GPU UUID：`GPU-c9ee2ea8-993d-e7e2-7e3f-7a183b63d573`
- Git commit：`fc55fea27f0ecfb4d55a4dff59912267d96c3dad`
- 正式随机种子：`15042/15043/15044`

## 排队与延迟解释

正式阶段的实时采样稳定观察到：

- `vllm:num_requests_running=8`
- `vllm:num_requests_waiting=8`
- GPU KV Cache 峰值约 13.52%
- GPU-Util 约 96%–97%
- 功耗约 149–150 W
- 温度最高约 70°C

waiting 请求不是“在 Prefill block 中等待”。它们尚未被调度为运行序列，通常也没有像 running 请求一样分配完整的 GPU KV Cache block；等已有请求完成、调度名额释放后，它们才进入 Prefill 和 Decode。

吞吐基本持平的直接原因不是“统计包含 waiting 请求”，而是 `max-num-seqs=8` 使 GPU 同时执行的序列仍只有约 8 条。吞吐的计时确实覆盖排队阶段，但 c8 已能持续补充并维持 8 条运行序列，c16 没有增加单位时间完成的请求数。

TPOT 主要衡量请求进入生成阶段后的逐 Token 间隔，不包含调度前的完整等待时间，所以 P95 TPOT 与 c8 几乎相同。TTFT 包含服务端排队时间；第二批请求大约要等待第一批完成，因此 P95 TTFT 增加约一个 5.5 秒的服务波次。E2E 包含 TTFT 和 Decode，因而接近 c8 的两倍。

## KV Cache 解释

c16 的 KV Cache 峰值仍约 13.52%，与 c8 基本一致。原因是使用 GPU KV Cache 的主要是 8 条 running 序列，而不是客户端全部 16 个未完成请求。waiting=8 证明调度并发受限，但不意味着 KV Cache 使用量翻倍。

按 c8 报告中的估算，当前实例约有 1427 个 GPU KV blocks、22832 个 Token slot、约 3.14 GiB KV Cache。13.52%约对应 193 blocks、3088 Token slot、0.424 GiB。它说明短请求实验远未达到 KV Cache 容量边界，但不能据此选择一个已经违反延迟 SLO 的客户端并发。

## 算术一致性

固定每请求输出 128 tokens：

```text
1.400667706 requests/s × 128 tokens/request
= 179.285466 tok/s
```

与汇总值一致。

E2E 近似复算：

```text
5471.729266 + 127 × 40.260742
≈ 10584.844 ms
```

与实测 Mean E2E `10583.944 ms` 相差约 0.90 ms（约 0.0085%），数据自洽。

## Short SLO v1 验证

| 指标 | SLO | c16 结果 | 判断 |
| --- | ---: | ---: | --- |
| 请求成功率 | ≥99% | 100% | PASS |
| P95 TTFT | ≤600 ms | 6015.515 ms | **FAIL** |
| P95 TPOT | ≤50 ms | 42.703 ms | PASS |
| P95 E2E | ≤6 s | 11.095 s | **FAIL** |
| 请求吞吐 CV（重复性） | ≤3% | 0.130% | PASS |

这是 SLO v1 在事前定义后的第一档正式验证。c16 虽然成功率和 TPOT 达标，但 TTFT 与 E2E 明显失败，因此不能作为当前 Short 场景的推荐客户端并发。

## 实验执行者复盘与校正

实验执行者的原始判断是：吞吐基本持平是因为 waiting 请求被计算进去；KV Cache 与 c8 一样；TPOT 只涉及单请求 Decode，而 E2E 把等待的 8 个请求算进去所以约翻倍；下一档选择 c16，因为 KV Cache 仍富足。

其中关于 KV Cache、TPOT 和 E2E 的核心方向正确，但需要补充两个边界：

1. 吞吐持平的根因是 `max-num-seqs=8` 没有扩大实际执行批宽，而不是单纯因为统计口径包含 waiting。
2. KV Cache 富余只能排除当前短请求的显存容量瓶颈，不能推翻延迟 SLO。c16 的 P95 TTFT 和 P95 E2E 已失败，因此当前推荐并发应选择 c8。

## 当前结论与边界

- **当前配置的吞吐平台**：c8→c16 输出吞吐只增加 0.27%，同时稳定出现 `running=8、waiting=8`，说明在 `max-num-seqs=8` 下吞吐拐点约在 c8。
- **SLO 容量**：c8 按 SLO v1 回看可通过；c16 是首次前瞻性验证且明确失败。当前测试范围内，Short 场景推荐最大客户端并发为 8。
- **KV Cache 容量**：峰值只有约 13.52%，KV Cache 未饱和；当前瓶颈是服务端并发上限及其后的排队，而不是 KV Cache 容量。
- **结论边界**：这里只找到了当前 `max-num-seqs=8` 配置下的平台，尚不能声称找到 A10、Qwen3-8B 或 vLLM 的全局硬件峰值。
