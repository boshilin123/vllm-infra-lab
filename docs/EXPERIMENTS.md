# 实验设计

## 1. 基线配置

首轮建议基线：

- 模型：Qwen3-8B BF16
- GPU：NVIDIA A10 23 GiB
- vLLM：0.9.1
- `max-model-len=4096`
- `max-num-seqs=8`
- `gpu-memory-utilization=0.85`
- 单副本、单 GPU

这是针对 23 GiB A10 和约 16 GiB BF16 权重的保守起点。`8192` 与更高 `max-num-seqs` 作为待测变量，不预先当作稳定基线。实际启动后，以显存余量和稳定性结果调整，并在所有报告中记录变更。

## 2. 工作负载

### 短请求

- 输入 256 tokens
- 输出 128 tokens
- 并发 1、2、4、8、16

### 长上下文

- 输入 1024 tokens
- 输出 256 tokens
- 并发 1、2、4、8

### Prefill / Decode 对照

- 短输入、长输出：观察 Decode 阶段和 TPOT
- 长输入、短输出：观察 Prefill 阶段和 TTFT
- 长输入、长输出：观察 KV Cache 压力与排队

### 突发流量

- 低负载稳定运行后快速提升请求速率
- 持续到副本扩容完成并恢复稳定
- 记录扩容前、扩容中、扩容后的指标

## 3. 参数实验

使用单变量法，其他参数保持基线不变：

- `gpu-memory-utilization`：0.80、0.85、0.90
- `max-num-seqs`：8、16、32
- `max-model-len`：4096、8192
- 并发数：1、2、4、8、16

若某项配置 OOM 或无法稳定启动，同样记录为运行边界，不静默删除失败结果。

## 4. 四个核心实验问题

1. **单副本饱和点：** 并发提高时，吞吐从哪一点开始收益下降，P95 和 waiting requests 何时明显上升？
2. **Prefill 与 Decode：** 输入/输出长度变化如何分别影响 TTFT、TPOT 和 GPU 利用率？
3. **KV Cache 配置边界：** `gpu-memory-utilization`、`max-num-seqs` 和 `max-model-len` 如何在容量、延迟和 OOM 风险之间取舍？
4. **突发流量与弹性：** 1 副本、2 副本和 HPA 在尾延迟、错误率、扩容时间和冷启动成本上有何差异？

每个实验都必须在报告中写明：假设、控制变量、实验结果、原因解释、适用边界。

## 5. 指标

客户端指标：

- TTFT
- TPOT / inter-token latency
- 端到端延迟
- P50、P95、P99
- requests/s
- input/output/total tokens/s
- 成功率与错误率

服务端指标：

- running requests
- waiting requests
- KV Cache 使用率
- prompt/generation token throughput
- 请求失败与重启次数

GPU 指标：

- GPU utilization
- framebuffer memory used
- power usage
- temperature

具体 Prometheus 指标名称以实际 vLLM 与 DCGM 版本为准，首次部署后固化查询表达式。

## 6. 运行规范

- 每个场景先预热，再进行正式采样。
- 每个配置至少重复三次，默认报告中位数，同时保留所有原始结果。
- 同一组对照实验尽量在相同节点和相近时间完成。
- 记录测试时间、Git commit、镜像版本、模型版本、节点和并存负载。
- 不只报告最高吞吐；同时报告尾延迟、错误率和资源代价。

### 6.1 Short 场景实验 SLO v1

从并发 16 实验开始，为单张 A10、Qwen3-8B BF16、256 输入/128 输出 Token 的 Short 场景使用以下服务等级目标：

| SLI | SLO |
| --- | ---: |
| 请求成功率 | ≥99% |
| P95 TTFT | ≤600 ms |
| P95 TPOT | ≤50 ms |
| P95 E2E | ≤6 s |

每档仍执行三轮正式实验，以三轮各自统计值的中位数进行 SLO 判定；同时保留每轮结果，若中位数通过但单轮明显越界，必须在报告中说明。请求吞吐 CV ≤3%作为实验重复性门槛，不属于服务体验 SLO。

这套阈值是在并发 8 完成后、并发 16 开始前确定的，因此不能将并发 8 回溯包装为预注册 SLO 验证。它用于判断后续提高并发或修改参数是否以不可接受的交互延迟换取吞吐。

## 7. 每轮实验后的复盘问答

每完成一个关键场景，先由实验执行者回答问题，再生成正式结论。问题至少覆盖以下四类：

1. **算术一致性：** 请求数、耗时、请求吞吐和 Token 吞吐能否通过单位换算相互验证？
2. **延迟组成：** TTFT、TPOT、输出长度和端到端延迟之间是否一致？
3. **稳定性与边界：** CV 或多轮差异能说明什么，又不能推广到哪些负载、硬件和时间范围？
4. **下一步假设：** 当前实验尚未回答什么，下一档并发或参数变化预计会出现什么现象？

回答时同时检查量纲。例如 `requests/s × tokens/request = tokens/s`；若单位无法约掉得到目标指标，计算关系就是错误的。复盘的目的不是背诵数字，而是确保每条结论都能由原始数据推导，并明确其适用边界。

## 8. 数据存储与简历门槛

首版不使用 MySQL、PostgreSQL 或 Redis。原始结果保存为 JSON/CSV，实验配置保存为 YAML，时序指标由 Prometheus 采集，汇总分析使用 Python/Pandas。只有当本地实验数量足以导致检索困难时，才考虑引入 SQLite 作为可选实验索引。

只有满足以下条件的数据才能写进简历：

- 可以从仓库脚本重新运行。
- 有原始结果文件和对应配置。
- 至少三次重复结果方向一致。
- 结论明确说明基线、变量和适用范围。
