# 项目实施方案

## 1. 项目目标

构建一个可复现的 Kubernetes 原生 vLLM 推理实验环境，并回答三个工程问题：

1. Qwen3-8B 在单张 NVIDIA A10 上的稳定运行边界是什么？
2. 并发、输入输出长度和 vLLM 参数如何影响 TTFT、TPOT、吞吐与尾延迟？
3. 多副本与基于请求队列的弹性策略能否在突发流量下改善 SLO？

项目结果必须由清单、脚本、原始数据和复现文档共同支撑，简历只引用已经完成并可复验的结论。

## 2. 与实习项目的边界

本项目负责推理数据面：模型服务、请求调度、性能、观测与弹性。

实习项目负责算力控制面：设备接入、GPU/NPU 抽象、vGPU、容量规划与平台资源治理。

HAMi 不进入本项目的主标题和核心验收项。若后续开展 GPU 配额实验，只作为独立扩展，不替代推理性能主线。

## 3. 实施阶段

### Phase 0：基线与安全边界

交付物：

- 固定 Kubernetes namespace 与资源命名。
- 记录可用节点、GPU、驱动、CUDA、模型和 vLLM 版本。
- 确认共享集群中现有工作负载，不停止或抢占无关服务。
- 为模型目录和实验结果制定持久化方案。

验收：环境事实可复查，实验不会依赖未记录的人工步骤。

### Phase 1：单副本推理服务

交付物：

- Deployment、Service 和健康检查；非敏感参数增多后再引入 ConfigMap。
- 固定版本的 vLLM 镜像与 Qwen3-8B 模型路径。
- OpenAI `/v1/models` 和 `/v1/chat/completions` 冒烟测试。
- 启动耗时、空闲显存和基础请求结果。

验收：删除并重建 Pod 后无需手工进入容器即可恢复服务。

### Phase 2：基准测试与参数实验

交付物：

- 固定长度的合成请求场景。
- 并发扫描与关键参数单变量实验。
- JSON/CSV 原始结果和汇总脚本。
- TTFT、TPOT、吞吐、P95/P99、错误率和 GPU 指标图表。

验收：同一配置至少重复三次，报告中说明预热、样本量和异常值处理。

### Phase 3：可观测性

交付物：

- vLLM ServiceMonitor 或等价抓取配置。
- 与现有 Grafana 版本兼容的可导入 Dashboard JSON；仅在个人/专用 Grafana 中持久化导入。
- vLLM 请求指标与 DCGM GPU 指标的统一时间线。
- 显存不足、请求排队或 Pod 重启等至少一个故障场景记录。

验收：全部 panel PromQL 对真实数据源验证，并能从统一时间线解释压测期间请求排队、KV Cache 与 GPU 利用率的关联。公司共享 Grafana 不属于本项目允许的写入范围时，以版本兼容 JSON、真实 PromQL 结果和等价 SVG 完成验收，不为截图突破安全边界。

### Phase 4：多副本与弹性

HPA（Horizontal Pod Autoscaler）是 Kubernetes 原生的水平副本自动伸缩控制器，可根据 CPU、内存或接入的自定义/外部指标调整 Deployment 副本数。KEDA（Kubernetes Event-driven Autoscaling）是事件驱动的伸缩组件，可从 Prometheus、消息队列等外部系统读取信号，并通常通过生成或管理 HPA 实现扩缩容。本项目只把两者作为候选实现；必须先完成只读能力与安全审计，再选择集群已有、权限可控且不影响公司服务的最小方案。

实施顺序固定为“只读安全审计 → 静态双副本容量与路由验证 → 自动弹性”。静态阶段还要用确定性 8/8 对照区分计算容量与入口分流：扩缩容负责改变副本容量，请求级路由负责把新请求送到更合适的副本，两者不能混为一个控制环。弹性边界为 `minReplicas=1、maxReplicas=2`；不使用服务启动后基本恒定的 DCGM framebuffer 显存占用作为扩容信号。候选主信号是持续的 waiting/queue，GPU、KV Cache、TPOT 与 SLO 用于解释瓶颈和约束决策。约数分钟的模型冷启动意味着纯反应式扩容可能无法改善 2～3 分钟的短突发，实验必须同时说明适用负载持续时间。

静态双副本测试不得通过 `kubectl port-forward service/...`判断负载均衡，因为该转发会固定选择一个后端 Pod。客户端应直接访问 ClusterIP，或在集群内访问 Service；验收必须按 `pod` 标签展示每副本 running/waiting 和请求分布。请求执行中不跨 Pod 迁移，因此还要识别 HTTP 长连接复用和连接级分配造成的不均衡。

交付物：

- 两副本部署与流量入口。
- 基于 waiting requests 的自定义指标或等价弹性信号。
- 突发流量脚本和扩容实验结果。
- 冷启动、扩容时间、扩容期间 P95 和错误率分析。

验收：能够说明策略适用条件、收益和冷启动带来的限制，而不只展示 HPA 成功扩容。

真实 least-inflight 入口实验已按 `PHASE4_ROUTER_EXPERIMENT.md` 的预注册指标、tmux约束和共享环境停止条件完成，并在实验后恢复单副本。该静态路由验证不等同于自动扩缩容；受155秒冷启动和公司集群权限边界约束，自动控制器仍只保留离线策略回放证据。

## 4. 技术约束

- Qwen3-8B BF16 权重约 16 GiB，单张 23 GiB A10 的 KV Cache 空间有限。
- 首轮实验将上下文限制在 4K/8K 范围，避免直接使用模型声明的最大上下文。
- 多副本实验需要至少两张可用 GPU，并需要模型权重可被目标节点访问。
- 共享集群的资源状态会变化；每次实验必须记录时间、节点和并存负载。
- 本个人项目在任何时刻最多使用两张 GPU；弹性配置的 `maxReplicas` 不得超过 2。
- 不停止、迁移或修改任何公司已有服务；所有写操作限定在本项目仓库和 `vllm-infra-lab` namespace。
- 第二张 GPU 必须先确认没有公司进程、Pod 或预留用途，并能通过受支持的调度方式安全隔离；无法保证具体设备不冲突时，不执行双副本扩容。
- 双 GPU 只用于 Phase 4 的短时受控实验，实验完成后恢复单副本；Phase 0–3 默认只使用一张 GPU。

## 5. 最终成果

- 一套可复现的 Kubernetes 部署清单。
- 一套有固定输入、参数和重复次数的基准测试。
- 一个可导入的 Grafana Dashboard。
- 一份包含原始数据、图表、结论和限制的性能报告。
- 2～3 条有真实量化结果、能经受面试追问的简历描述。
